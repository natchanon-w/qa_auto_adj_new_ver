========================================================
  QA GUIDE: transfer_offus - Test Data Generator & Uploader
========================================================

OVERVIEW
--------
This tool generates encrypted CSV test data for the
payment-bulk-adj-transfer-offus-processor reconcile pipeline,
then uploads it to S3.

A real off-us reconcile batch bundles up to 4 file variants
together (the processor lists every control JSON under
base_path in one pass):

  inbound_promptpay        -> TRANSFER_OFF_US_INBOUND_PROMPTPAY_RECONCILE_AUTO_ADJUST_<date>.csv
  inbound_actual_account   -> TRANSFER_OFF_US_INBOUND_ACTUAL_ACCOUNT_RECONCILE_AUTO_ADJUST_<date>.csv
  outbound_promptpay       -> TRANSFER_OFF_US_OUTBOUND_PROMPTPAY_RECONCILE_AUTO_ADJUST_<date>.csv
  outbound_actual_account  -> TRANSFER_OFF_US_OUTBOUND_ACTUAL_ACCOUNT_RECONCILE_AUTO_ADJUST_<date>.csv

By default `generate` produces all four into ONE work dir
(matching a real batch); pass a comma-separated subset to
generate only some of them.

Each variant posts to a different source table:
  inbound_promptpay        -> credit_transfer_inbound        (ref: ctfi_txn_ref_id, status: ctfi_status, reset to PRCS)
  inbound_actual_account   -> actual_credit_transfer_inbound  (ref: acti_txn_ref_id, status: acti_status, reset to PRCS)
  outbound_promptpay       -> credit_transfer                 (ref: payment_txn_ref, status: status, reset to PRCS)
  outbound_actual_account  -> actual_credit_transfer           (ref: payment_txn_ref, status: status, reset to PRCS)
  "ref" is the column the auto-adjustment update-status API matches the
  file's transaction_reference_id on (release-cb consumers) — the update /
  delete scripts use it too.


KNOWN ISSUES FOUND WHILE BUILDING THIS TOOL (read before debugging "why didn't
my test file get classified")
----------------------------------------------------------------------------
1. SPELLING: the processor's own code (app/batch/constants.go,
   config.yaml's response_file_name_map) spells the promptpay prefix
   "PROMTPAY" (missing a P). Real production files from upstream are
   spelled correctly "PROMPTPAY". Confirmed still present as of the
   processor repo's latest commit. This tool generates the CORRECT
   "PROMPTPAY" spelling (matching real prod) — which means testing against
   the current deployed processor will reproduce the live bug where
   AdjustmentType comes out empty for promptpay files. If you need a
   "clean" happy-path test against the current (buggy) code instead,
   rename the generated files/control-json table refs from PROMPTPAY to
   PROMTPAY before uploading.

2. ENCRYPTION: real production files ARE PGP-encrypted (confirmed via S3
   downloads — compression: "PGP", filenames end in .csv.encrypted). This
   tool encrypts. The processor repo's own local-scripts/generate_test_data.py
   does NOT encrypt (uploads plain .csv) — that still "works" against the
   processor because decryption is skipped for filenames not ending in
   ".encrypted", but it isn't representative of what real upstream sends.

3. CONTROL JSON FORMAT: real production control JSON uses
   dataset "spending", table "transfer_off_us_<type>_auto_adjust", sha256
   checksum, compression "PGP" — different from the stale local script,
   which uses dataset "VFS-DCB", sha256-but-empty-compression. This tool
   matches the real format (verified against actual S3 downloads).

4. UPLOAD PATH: files go straight to base_path
   (s3://bucket/dp/adjustment/transfer-off-us/<date>/<file>) — the processor's
   s3_base_path is "dp/adjustment/transfer-off-us", no "request/" subfolder.

5. INBOUND ACTUAL ACCOUNT ROWS MATCH THE ONLINE PATH (2026-10-08, VBFS-9465):
   the actual_credit_transfer_inbound row is written the way the online
   inbound path (lookup / transfer / processor consumers) writes it, because
   savedb builds the auto-adjustment TM message from this row:
   - PII columns are AES-GCM encrypted with the env's key (SIT has
     aes.gcm.enable=true): acti_from_acct_id (sender account no),
     acti_from_acct_name, acti_from_display_name, acti_from_tax_id,
     acti_to_acct_no, acti_to_acct_name, acti_to_display_name,
     acti_to_cif_no, acti_receiver_tax_id, acti_to_pocket_no.
     A plaintext value there makes savedb's decrypt throw: the API still
     answers 0000 and the status changes, but NO TM (COMPLETED) / CLOG
     (FAILED) message is sent.
   - acti_to_acct_no / acti_to_pocket_no / acti_to_acct_id / acti_from_acct_id
     are the same values as the CSV row's vfs_to_account_no /
     vfs_to_pocket_no / vfs_to_tm_account_id / vfs_from_account_no.
   - acti_to_cif_no (15 digits) is set, so TM toCustomerId can be checked.
   - acti_status PRCS (not PROCESSING), acti_tfr_ref_no = a DCB-style pibId,
     acti_transfer_dtm set, acti_to_acct_bank_code 088, from bank = from
     branch = sending id 004, from (not to) internal account id.

6. ALL FOUR TYPES MATCH THE ONLINE PATH (2026-10-08, checked on release-cb):
   same idea as item 5 for the other three tables.
   - inbound_promptpay (payment-inbound-j-promptpay-transfer-savedb-consumer):
     API matches ctfi_txn_ref_id; ctfi_req_id = request UUID,
     ctfi_tfr_ref_no = 20-digit DCB pibId; ctfi_status PRCS. Encrypted
     (decrypted by savedb when aes.gcm.enable=true): ctfi_from_acct_id,
     ctfi_from_acct_name, ctfi_from_display_name, ctfi_from_tax_id,
     ctfi_to_any_id, ctfi_to_acct_name, ctfi_to_display_name,
     ctfi_to_acct_no, ctfi_to_pocket_no. ctfi_from_acct_id / ctfi_to_acct_id /
     ctfi_to_acct_no / ctfi_to_pocket_no = CSV vfs_from_account_no /
     vfs_to_tm_account_id / vfs_to_account_no / vfs_to_pocket_no;
     ctfi_transfer_dtm set.
   - outbound_promptpay / outbound_actual_account
     (payment-outbound-j-{promptpay,actacct}-transfer-response-consumer):
     API matches payment_txn_ref (ref_id = request UUID); status PRCS.
     Encrypted: from_account_no, from_pocket_no, from_account_name_th,
     from_account_name_en, from_account_display_name, sender_tax_id,
     to_account_no, to_account_name, to_account_display_name,
     receiver_tax_id (+ to_any_id for promptpay). These consumers decrypt
     ALWAYS — no aes.gcm.enable check and no blank check — so every one of
     these columns must hold a ciphertext: a NULL / '' / plaintext value
     there means no TM / CLOG message. from_account_no / from_pocket_no /
     from_account_id / to_account_no = CSV vfs_from_account_no /
     vfs_from_pocket_no / vfs_from_tm_account_id / vfs_to_account_no;
     sender / receiver tax id and transfer_dtm set.


REQUIREMENTS
------------
- Go 1.21+  (run: go version)
- AWS CLI   (run: aws --version)
- AWS profile configured in ~/.aws/credentials
- public.pgp and private.pgp must be present in this folder
- The active env's "encryption_key" in config.json must be the AES_GCM_KEY
  of that env's off-us consumers (the inbound savedb and outbound
  transfer-response consumers; non-PRD envs only, kept in config.json the
  same way as repayment). Env var AES_GCM_KEY overrides it. --plain only for
  an env with aes.gcm.enable=false, and only for the inbound types — the
  outbound consumers always decrypt (item 6).


CONFIGURATION
-------------
  Select the env to test with "active_env" (same as repayment):

  {
    "active_env": "sit",                     <- "sit" or "uat"
    "environments": {
      "sit": {
        "bucket":         "cb-core-bank-th-sit-s3-payment-reconcile",
        "base_path":      "dp/adjustment/transfer-off-us/2026-01-10/",
        "aws_profile":    "s3-cb-sit-th-dpp",
        "region":         "ap-southeast-7",
        "encryption_key": "..."
      },
      "uat": {
        "bucket":         "cb-core-bank-th-uat-s3-payment-reconcile",
        "base_path":      "...",
        "aws_profile":    "s3-cb-uat-th-dpp",
        "region":         "ap-southeast-7",
        "encryption_key": "..."
      }
    }
  }

  - region: passed as --region to every aws call; SIT and UAT buckets are
    both in ap-southeast-7. Empty = let the profile decide.
  - encryption_key: used by generate for the PII columns of all four types.
  - generate and upload both print the active env — check it before uploading.
  - base_path: dp/adjustment/transfer-off-us/<date>/ — no "request/" (item 4).


STEPS
-----

STEP 1 — Generate test data
  Command:
    go run . generate <records> [types] [--plain]

  Examples:
    go run . generate 5                                  # all 4 types
    go run . generate 5 outbound_promptpay                # just one
    go run . generate 5 outbound_promptpay,inbound_promptpay
    go run . generate 2 inbound_actual_account            # 1 COMPLETED + 1 FAILED

  Output (work/<timestamp>/):
    - raw_inbound_promptpay.csv        (only for selected types)
    - raw_inbound_actual_account.csv
    - raw_outbound_promptpay.csv
    - raw_outbound_actual_account.csv
    - state.json   (internal state, do not edit)

  Tip: edit the raw_<type>.csv files before finalize if needed.


STEP 2 — Finalize (encrypt + verify)
  Command:
    go run . finalize

  What it does, per selected type:
    - Encrypts the raw CSV using public.pgp
    - Verifies using private.pgp (SHA256 checksum)
    - Writes one control JSON per type

  Then across all types:
    - insert_transfer_offus_transactions.sql
    - update_transfer_offus_transactions.sql
    - delete_transfer_offus_transactions.sql
    (each statement targets that row's own source table)


STEP 3 — Upload to S3
  Command:
    go run . upload [dir] [--keep]

  Target:
    s3://<bucket>/<base_path>   (e.g. dp/adjustment/transfer-off-us/2026-01-10/)


FULL EXAMPLE
------------
  go run . generate 5
  go run . finalize
  go run . upload


NOTES
-----
- The date in output filenames is taken from the first YYYY-MM-DD
  segment found anywhere in base_path, NOT from today's date.
- SQL files insert/update/delete against 4 different source tables
  in one shared script — see the per-type table mapping above.

CHECK THE TM MESSAGE (inbound_actual_account, COMPLETED row)
  On topic payment.common.transaction.downstream.TM, for the txn ref:
    toAccountNo        = vfs_to_pocket_no (plaintext, not ciphertext)
    toAccountComment   = "TR to " + vfs_to_account_no
    toCustomerId       = the 15-digit acti_to_cif_no (decrypted)
    fromAccountNo      = vfs_from_account_no
    toBranchCode       = 0000
    transactionFee     = acti_sender_fee_amt (0.00)
    Kafka key          = acti_sending_bank_rrn
    header x-requester = ITMX
  No message at all = check savedb log for a decrypt error (wrong
  encryption_key for the active env).
